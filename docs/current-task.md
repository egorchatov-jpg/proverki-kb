56. **pkb-v464 — ТРЕТЬЯ, вероятно решающая причина: гонка между конкурентными self-heal вызовами разных клиентов затирала друг друга и никогда не давала БД устояться:**
   - **Контекст:** после pkb-v463 (`/health` больше не 503, Timeweb больше не убивает контейнер по этому поводу) production ВСЁ РАВНО оставался с `recordCount: 0` спустя много минут стабильной работы без новых деплоев. Свежий runtime-лог показал тот же паттерн `[persist] force wipe + pull into: ...` повторяющийся каждые 1-9 минут, БЕЗ новых деплоев между повторами — значит причина уже не Timeweb-рестарты, а что-то внутри самого работающего процесса.
   - **Настоящая причина:** `index.html` → `recoverRecordsWhenServerEmpty()`, вызывается из `loadFromServer()` при **каждой** загрузке приложения, если сервер отвечает пустым списком записей (`d.records.length === 0`) — что верно для абсолютно всех активных пользователей/вкладок всё то время, пока БД реально пуста. Она дёргает `GET /api/self-heal` (публичный, без авторизации — специально, как recovery-путь для клиентов). `server.js` → `/api/self-heal`, при `recordCount === 0`, вызывал `forcePullDbFromGithub()`, которая делает `wipeLocalDbFiles()` (удаляет файл БД) **затем** скачивает и записывает свежую копию. Эта пара операций не была защищена от параллельного вызова — при нескольких открытых клиентах (или просто нескольких вкладках/устройствах одного пользователя) каждый независимо стирал и заново качал файл БД **одновременно**, поэтому один вызов почти всегда стирал файл, который другой вызов только что успешно скачал и записал — из-за этого локальная БД никогда не оставалась населённой достаточно долго, чтобы следующий обычный запрос (список записей, фото) увидел в ней данные, что порождало бесконечный самоподдерживающийся цикл «пусто → все клиенты одновременно лечат → гонка стирает результат → снова пусто → …».
   - **Исправление:** `lib/github-persist.js` → `forcePullDbFromGithub()` теперь защищена мьютексом (`_inFlightForcePull`) — если пул уже выполняется, конкурентные вызовы дожидаются того же самого результата вместо того, чтобы начинать свой собственный `wipeLocalDbFiles()`+пул. Также добавлено логирование итогового результата пула (`[persist] force pull result: {...}`) для диагностики, успешен ли сам пул с GitHub независимо от гонки.
   - **Не тронуто (сознательно):** `recoverRecordsWhenServerEmpty()`/`self-heal` сама логика восстановления не изменена — это штатный и полезный recovery-путь; проблема была исключительно в отсутствии взаимного исключения при параллельных вызовах.
   - **Проверено:** `node --check` для `lib/github-persist.js`. Эффект на production ещё предстоит подтвердить после деплоя (см. чеклист) — конкретно нужно смотреть, перестанут ли повторяться `force wipe + pull` в логах, и стабилизируется ли `recordCount` в `/health` на положительном значении.
   - `APP_VERSION` → `1.16`, `APP_BUILD` / SW cache → `pkb-v464`.

55. **pkb-v463 — вторая причина: production в бесконечном crash-restart-loop из-за `/health`, база данных реально была пуста (частично устранено — см. pkb-v464 выше для полной картины):**
   - **Контекст:** пользователь продолжал не видеть фото даже после ручного деплоя pkb-v462. Прямая HTTP-проверка `/health` на production стабильно отдавала `503` даже спустя минуты после деплоя; `/photos/<filename>` для всех названных файлов отдавал 404 или обрыв соединения. Пользователь прислал runtime-логи приложения из панели Timeweb (не логи сборки — логи самого работающего процесса, формат PM2 `0|index`).
   - **Ключевые строки лога:** `[persist] db push error: Local database missing: /tmp/proverki-kb/proverki.db`, и раз за разом, каждые несколько минут, повторяется цикл `[data] Using /tmp for SQLite ...` → `[persist] force wipe + pull into: ...` → `[persist] refusing to push database with no records`. То есть процесс приложения **перезапускался целиком снова и снова**, каждый раз стирая и заново пытаясь скачать БД с GitHub — и, судя по повторяющемуся `refusing to push database with no records`, не успевал закончить восстановление до следующего перезапуска. Production реально работал (местами) с пустой БД, что подтверждено `GET /health` → `{recordCount:0, dbFileBytes:4096}` в отдельной прямой проверке.
   - **Причина (частичная — устраняла один из двух источников restart/wipe):** `server.js`, эндпоинт `GET /health` возвращал HTTP `503`, если `recordCount` ещё `0` (типичная ситуация в первые секунды/минуты после старта, пока асинхронный `bootstrapGithubPersist()`/`pullDbFromGithub()` ещё тянет снапшот с GitHub). Timeweb App Platform (процесс управляется PM2 — префикс `0|index` в логах) использует `/health` как **healthcheck контейнера**. Получая `503` во время нормального, штатного восстановления БД, Timeweb решал, что контейнер «нездоров», и убивал/пересоздавал его — что стирало эфемерный диск `/tmp` и запускало восстановление с нуля заново.
   - **Исправление:** `/health` теперь **всегда** отвечает HTTP `200`, пока сам процесс Node.js жив и принимает соединения — независимо от того, восстановлена ли уже БД. Фактическое состояние БД (`ok`, `recordCount`, `bootstrapping` и т.п.) осталось в JSON-теле ответа для мониторинга/отладки, но больше не транслируется в HTTP-статус.
   - **Важно — этого фикса оказалось НЕДОСТАТОЧНО:** после деплоя pkb-v463 `/health` стабильно отдавал 200, Timeweb больше не убивал контейнер (подтверждено — не было новых `Container started`/build-циклов в логах), но `recordCount` в `/health` продолжал быть `0` несколько минут подряд, и в runtime-логе продолжался тот же паттерн `force wipe + pull` без явных деплоев между повторами — это вскрыло вторую, независимую причину (гонка конкурентных self-heal вызовов, см. pkb-v464 выше).
   - **Проверено:** `node --check` для `server.js`.
   - `APP_VERSION` → `1.15`, `APP_BUILD` / SW cache → `pkb-v463`.

54. **pkb-v462 — расследование «куда делись прикреплённые к проверкам фотографии» (изначальная гипотеза этой сессии — верная, но НЕ единственная причина, см. pkb-v463/pkb-v464 выше для полной картины):**
   - **Жалоба пользователя:** фотографии, прикреплённые к проверкам, вообще не отображаются — проблема наблюдалась на всех записях с фото, конкретно упомянуты проверки №115526, 118726, 120126, 121026.
   - **Проверка целостности данных на сервере (важно — данные НЕ потеряны):** скачаны и напрямую открыты через `node:sqlite` три снапшота production БД из `github.com/egorchatov-jpg/proverki-kb-data` (коммиты 2026-08-29 05:23, 05:41, 09:02 UTC) — во всех трёх таблица `photos` содержит все 10 строк для всех 6 проверок с фото (включая все 4 названные пользователем), и все 10 файлов `*.avif` физически присутствуют в `photos/` репозитория данных. То есть на уровне БД+файлового резерва фотографии никогда не пропадали — реальной потери данных на сервере нет.
   - **Найденная и устранённая настоящая причина (реальный баг, воспроизводимый как временная гонка):** `api/photos.js`, эндпоинт `GET /api/photos/list/:checkId` — при каждом запросе списка фото для проверки сервер фильтровал строки БД по `fs.existsSync()` на **локальном эфемерном диске** Timeweb и **немедленно и безвозвратно удалял** («DELETE FROM photos») любую строку, чей файл в этот момент не находился на диске. Диск Timeweb пересоздаётся при каждом редеплое, а сами фото восстанавливаются на него асинхронно из GitHub-репозитория данных функцией `pullMissingPhotosFromGithub()` при старте сервера (`bootstrapGithubPersist()`). Если клиент запрашивал список фото для проверки в узком окне после редеплоя, пока это асинхронное восстановление ещё не дошло до конкретного файла, эндпоинт видел «файла нет» и стирал связь фото↔проверка из БД навсегда — при этом сам файл на GitHub оставался целым, но приложение уже не знало о его существовании. Это объясняет, почему в БД на сервере всё оказалось цело (проверка была сделана после того, как гонка либо не успела произойти, либо уже сама восстановилась при следующем открытии, до следующего редеплоя), но пользователь тем не менее наблюдал пустой список фото в моменте.
   - **Исправления:**
     - `api/photos.js` → `/list/:checkId`: убрано автоматическое `DELETE FROM photos` по признаку отсутствия файла на диске. Теперь эндпоинт всегда возвращает все строки БД (источник истины) — фильтруется только небезопасное имя файла (защита от path traversal), а не факт наличия файла.

55. **pkb-v463 — НАСТОЯЩАЯ причина «фото пропали» (эта сессия, продолжение): бесконечный crash-restart-loop production из-за `/health`, база данных реально была пуста:**
   - **Контекст:** пользователь продолжал не видеть фото даже после ручного деплоя pkb-v462. Прямая HTTP-проверка `/health` на production стабильно отдавала `503` даже спустя минуты после деплоя; `/photos/<filename>` для всех названных файлов отдавал 404 или обрыв соединения. Пользователь прислал runtime-логи приложения из панели Timeweb (не логи сборки — логи самого работающего процесса, формат PM2 `0|index`).

То есть процесс приложения **перезапускался целиком снова и снова**, каждый раз стирая и заново пытаясь скачать БД с GitHub — и, судя по повторяющемуся `refusing to push database with no records`, не успевал закончить восстановление до следующего перезапуска.    - **Настоящая причина (root cause всей сессии, не только фото):** `server.js`, эндпоинт `GET /health` возвращал HTTP `503`, если `recordCount` ещё `0` (типичная ситуация в первые секунды/минуты после старта, пока асинхронный `bootstrapGithubPersist()`/`pullDbFromGithub()` ещё тянет снапшот с GitHub). Timeweb App Platform (процесс управляется PM2 — префикс `0|index` в логах) использует `/health` как **healthcheck контейнера**. Получая `503` во время нормального, штатного восстановления БД, Timeweb решал, что контейнер «нездоров», и убивал/пересоздавал его — что стирало эфемерный диск `/tmp` и запускало восстановление с нуля заново, а новый процесс почти наверняка снова не успевал закончить пул БД до следующей healthcheck-проверки. Результат — самоподдерживающийся бесконечный цикл перезапуска, при котором БД **никогда** не успевала полностью восстановиться, а сервер обслуживал реальные пользовательские запросы (список проверок, фото и т.д.) той пустой/недовосстановленной локальной БД, какая была на момент запроса в моменте между перезапусками. Это объясняет и «фото пропали», и потенциально куда более широкий класс проблем (частично пустые списки проверок, случайные 404 и обрывы соединений), если бы это продолжилось дальше.
   - **Почему это не проявлялось раньше:** до этой сессии `/health` почти всегда успевал получить `recordCount > 0` до истечения грейс-периода Timeweb (базы меньше, GitHub API быстрее отвечал), поэтому цикл рестартов не зацикливался бесконечно — обычно достаточно одного успешного цикла «пул → recordCount>0 → health 200» чтобы вырваться из цикла. Не выяснено окончательно, что именно сделало на этот раз восстановление настолько медленным/ненадёжным, что цикл не мог завершиться — не критично для исправления (описанного ниже), но стоит иметь в виду, если проблема повторится.
   - **Исправление:** `/health` теперь **всегда** отвечает HTTP `200`, пока сам процесс Node.js жив и принимает соединения — независимо от того, восстановлена ли уже БД. Фактическое состояние БД (`ok`, `recordCount`, `bootstrapping` и т.п.) осталось в JSON-теле ответа для мониторинга/отладки, но больше не транслируется в HTTP-статус. Это устраняет сам механизм, из-за которого Timeweb мог убивать контейнер во время легитимного, штатного восстановления БД.
   - **Не тронуто:** `GET /api/version` уже до этой сессии не имел такой проблемы — `databaseOk` там означает только «файл SQLite открывается», не «содержит данные», и никогда не отдавал 503.
   - **Проверено:** `node --check` для `server.js`. Не удалось воспроизвести сам crash-loop локально (специфично для окружения Timeweb/PM2 healthcheck) — исправление обосновано логами production и логикой кода, но эффект в проде предстоит подтвердить после деплоя (см. чеклист).
   - `APP_VERSION` → `1.15`, `APP_BUILD` / SW cache → `pkb-v463`.

     1. **Реальный краш в JS, а не просто нестрогая логика.** `applyPendingUpdates()` и `purgeSyncedUpdates()` вызывали `.trim()` на каждом значении поля из очереди обновлений (`updateQueue`) без проверки типа. При редактировании записи с заполненным чек-листом `fields` содержит `checklistFilled` (`boolean`) и `checklistViolations`/`checklistQuestionTexts` (`object`/`null`) — вызов `.trim()` на них выбрасывает исключение. Поскольку `applyLoadedRecords()` не оборачивает эти вызовы в `try/catch`, вся цепочка промисов `loadFromServer()` обрывается по необработанному исключению **до** того, как локальные изменения будут гарантированно применены и до вызова `migrateSamoproverkaToSamootsenka()` — отсюда оба симптома сразу.
     2. **Устаревшая логика "server wins", оставшаяся от Excel-эпохи.** Даже без краша, `applyPendingUpdates()` содержал правило: если у сервера **уже есть какое-то** (пусть и другое/устаревшее) значение поля — считать его окончательным и не применять ожидающее изменение из очереди, при этом **всё равно удаляя** запись из очереди как «синхронизированную» (баг в самой логике `allSynced`, не выставлявшей `false` в этом случае). Раньше (до перехода на SQLite) сервер = Excel-файл, который мог не успеть обновиться, и такая защита была осмысленной; сейчас сервер синхронно пишет в SQLite и подтверждает `success:true` только после реальной записи, поэтому это правило только теряло изменения.
     3. **Отдельная причина возврата «Самопроверка»:** серверная миграция в `lib/db.js` (`migrateDropInspectorColumn`) переносила только `'Самооценка' → 'Техресурс'`, но не `'Самопроверка'`. Прямая проверка dev-базы (`SELECT DISTINCT method FROM records`) подтвердила, что значение `Самопроверка` физически оставалось в SQLite. Клиентская функция `migrateSamoproverkaToSamootsenka()` правит только `appState.db` в браузере и никогда не отправляет исправление на сервер — поэтому старое значение неизбежно возвращалось при каждой следующей загрузке данных.
   - **Исправления:**
     - Добавлена безопасная функция `fieldValuesEqual(a, b)` (сравнение с приведением к строке для строк, `JSON.stringify` для объектов/boolean, без падения на типах) и `fieldValueIsEmpty(v)`; `applyPendingUpdates()` и `purgeSyncedUpdates()` переписаны на них.
     - `applyPendingUpdates()`: теперь при несовпадении значений локальное (ещё не подтверждённое) значение **применяется** к отображаемой записи и **остаётся в очереди** до тех пор, пока сервер не подтвердит именно это значение — вместо тихой потери изменения.
     - `seedUpdateQueueFromLocalDb()`: теперь повторно ставит поле в очередь не только когда у сервера пусто, но и когда у сервера **другое** значение, чем локально.
     - `lib/db.js`: серверная миграция расширена — `UPDATE records SET method = 'Техресурс' WHERE method IN ('Самооценка', 'Самопроверка')`, исправляет значение непосредственно в SQLite (и через `flushDbPersist`/GitHub во всех дальнейших пуллах), а не только на экране одного клиента.
   - **Проверено:** прямой SQL-запрос к dev-базе подтвердил, что `Самопроверка` пропадает после перезапуска сервера с новой миграцией; 8 unit-тестов через изолированный Node `vm` harness покрывают отсутствие исключений на чек-лист-полях, применение и хранение в очереди несовпадающего значения до подтверждения сервером, точное совпадение для удаления из очереди, и повторную постановку в очередь при отличии локального значения от серверного.
   - `APP_BUILD` / SW cache → `pkb-v457`.
48. **pkb-v456 — исправление отката настроек и ложного «неверный пароль»:**
   - **Баг 1 — чекбоксы в окне «Организации» слетали после повторного входа:**
     - Причина найдена через логи production (Timeweb API): множественные записи `[settings] rejected master write: stale_client`. `settingsUpdatedAt` — общий токен optimistic concurrency для **всех** окон настроек. Если между открытием окна и сохранением на сервер попадала любая другая запись настроек (другая вкладка/устройство, миграция хеша пароля при логине), сервер отклонял `PUT /api/settings` как устаревший (`409 stale_client`), а клиент **безусловно** принимал серверную версию (`applyMasterSettingsPayload`), затирая только что сделанные изменения.
     - Исправление в `syncSettingsToServer()`: перед отправкой делается снимок локальных правок (`orgs`, `barriers`, `barriersConfig`, `barriersPK`, `barriersCustomPassports`, `passwords`, `usedPasswords`). При `stale_client` клиент подхватывает свежую базовую ревизию с сервера, но **переналагает локальные правки сверху** и повторяет попытку (до 3 раз), вместо того чтобы их терять.
     - Это защищает все окна настроек, использующие общий механизм синхронизации, а не только «Организации».
   - **Баг 2 — пароль суперпользователя не проходил после восстановления сети (более часа):**
     - Проверка `SUPERUSER_PIN`/`AUTH_ENFORCE` на production через Timeweb Cloud API подтвердила, что переменные окружения корректны; прямой тест логина через API тоже прошёл успешно.
     - Настоящая причина: пароль суперпользователя не хранится на клиенте (только серверный `scrypt`-хеш, по дизайну безопасности). Любая ошибка сети/сервера, отличная от `401` (таймаут, 5xx, обрыв соединения), в `checkPin()` ошибочно вела в ту же ветку «Неверный пароль», хотя сервер на самом деле не был доступен для проверки.
     - Исправление: только явный `401` считается настоящим неверным паролем. Любая другая ошибка сначала пробует локальный офлайн-фолбэк (работает для admin/inspector/организаций — у них есть локальная копия пароля), а если не подходит — повторяет запрос к серверу до 2 раз и только затем показывает честное сообщение «Нет связи с сервером» вместо ложного «Неверный пароль». Офлайн-вход для суперпользователя остаётся невозможным по дизайну (подтверждено пользователем как ожидаемое поведение, не баг).
   - Оба исправления протестированы через изолированные unit-тесты (Node `vm` harness) — retry с сохранением правок при `stale_client`, и три сценария `checkPin` (реальный 401, офлайн с локальным фолбэком, офлайн без фолбэка → retry → честное сообщение).
   - `APP_BUILD` / SW cache → `pkb-v456`.
